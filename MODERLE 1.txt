Phrase jury

« La CI décide si la release peut passer. Le ML ne remplace pas cette règle : il apprend sur l’historique Medianet combien les vulnérabilités sont difficiles à corriger, enrichit cette estimation avec le contexte externe, puis la compare à la date client afin de prioriser les corrections qui risquent de retarder la mise en production. »

Phase 5 — Écran Release Readiness
5.1 Endpoint
GET /api/projects/{id}/release-readiness
Auth = même visibilité que le projet.

Calcul

Client.releaseDeadline, releaseLabel
Dernier scan COMPLETED par repo du projet
CVE encore présentes
blocking = exactement la règle CI (kevListed OU CRITICAL/HIGH)
Predict batch (proba + jours)
repoCount actuel = exposition (affichage). La feature d’entraînement reste celle à first_seen.
estimatedRemediationDays = max(estimatedDays) des bloqueurs (chemin critique v1)
daysRemaining = deadline − today (null si pas de deadline)
5.2 Risque de retard — v1 puis MAE
v1 acceptable (documentée)
Marge fixe 2 jours :

ÉLEVÉ si estimated > daysRemaining
MOYEN si estimated ∈ [daysRemaining − 2, daysRemaining]
FAIBLE sinon
Pas de deadline → delayRisk = null (liste seulement)
daysRemaining < 0 → ÉLEVÉ
Cible (dès que metrics_reg.json a un MAE)
Ne pas traiter estimated = 4 et J-5 comme « large » si MAE = 2,7.

intervalle ≈ [estimatedDays − MAE, estimatedDays + MAE]
exemple : 4 ± 2,7  →  [1,3 ; 6,7]
Condition	Risque
estimated + MAE ≤ daysRemaining
FAIBLE
estimated ≤ daysRemaining < estimated + MAE
MOYEN (la borne haute dépasse)
estimated > daysRemaining
ÉLEVÉ
daysRemaining < 0
ÉLEVÉ
Exemple du jury : J-5, ~4 j, MAE 2,7 → borne haute 6,7 > 5 → MOYEN, pas FAIBLE.
On écrit dans le rapport : v1 = marge 2 j ; dès MAE connu, le risque utilise l’intervalle.
